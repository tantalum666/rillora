# Privacy-Filtered Product Event Contract

Role: focused first-party event contract  
Authority scope: current local MVP event names, properties, provenance and retention boundary  
Superseded by: later explicit privacy, consent or analytics decision  
Do not use for: market evidence, third-party analytics approval or production retention compliance  
Status: LOCAL SERVER-GENERATED CONTRACT IMPLEMENTED; EXTERNAL COLLECTION CLOSED  
Last updated: 2026-10-03 (retention implementation/evidence reconciliation)

## Purpose

The MVP needs enough measurement to test whether planners make useful progress without copying sensitive plan content into an analytics system. Events are therefore generated by the API after successful domain mutations, stored in the same tenant-isolated PostgreSQL boundary and restricted to exact low-cardinality properties.

There is no arbitrary client tracking endpoint and no third-party analytics SDK.

The database check constraint enforces the exact key set and enumerated values for each event. Titles, institution names, contact data, account hints, locations, values, currencies, free text, invitation capabilities, ciphertext and identity-provider identifiers are forbidden.

## Future Commercial Events — DESIGNED, NOT IMPLEMENTED

`pricing_viewed`, `subscription_started`, `subscription_refunded`, `subscription_cancelled`, `plan_reviewed_30d` and `plan_maintained_90d` are named in the MVP measurement contract but are not part of the current local write allowlist. They cannot be emitted until payment remains within scope and a separate schema/privacy decision defines exact low-cardinality properties.

Commercial amounts, tax, fees, cash settlement, invoice/provider IDs and recognized revenue belong in the tenant-safe commerce/finance ledger, not in a generic analytics payload. Future reviewed low-cardinality properties may include immutable `price_code`, plan/offer version, billing period, purchase-route-policy version and coarse cohort. Do not persist the ephemeral Storefront to a customer profile or generic marketing analytics; never include card data, plan content or contact identity. Unit-economics requirements are in [`unit-economics.md`](unit-economics.md).

September 10 packaging review defines the future measurement sequence in
[monetization.md](monetization.md): completed recipient acceptance and comprehension,
an eligible activated household's paid intent, actual offer exposure/payment,
then meaningful 30/90-day maintenance. Sharing audit events are not automatically
part of this product-event schema. Implement and review the exact schema and
retention/cleanup before measurement; this document change deploys no tracking.

## Provenance And Write Path

- Events are appended in the same database transaction as the successful product mutation; failed or rolled-back mutations do not produce progress events.
- The client may send only the coarse provenance header `x-rillora-client: web|ios`. Missing or invalid values are stored as `unknown`.
- Web planner requests identify as `web`; iOS planner requests identify as `ios`; public synthetic-recipient calls deliberately send no planner provenance header.
- The application database role has `INSERT` access only. It cannot select, update or delete event rows. Forced RLS preserves planner isolation.
- Event schema version is currently `1`.

## Retention Truth

Each row receives an `expires_at` deadline90days after creation. The bounded retention worker and enabled heartbeat alarms were deployed in the September30 release work. Independent legal/security holds and idempotent privacy replay remain part of deletion. October3 adds a locally tested hold/cleanup serialization repair; it is not yet deployed. A deadline, heartbeat or local test does not prove deletion of a specific production row. Consent/notice, lawful aggregation and operator-access boundaries remain. See [retention/recovery](recovery-control-journal.md) and [strict review](code-review-20261002.md).

## Evidence Boundary

API integration tests verify exact properties, invalid-source degradation to `unknown`, forced RLS, insert-only runtime privileges, the 90-day marker and database rejection of an extra sensitive-looking property. Web and iOS tests verify planner provenance and confirm public rehearsal requests omit it. The historical local regression baseline was API 40/40, Web API-client 13/13 and iOS 71/71; those totals include later first-use work while preserving the event-contract coverage described here.

After the native-only OIDC configuration regression was added, the historical overall API baseline became 41/41; the event contract itself did not change.

This is local implementation evidence only. It is not a production analytics pipeline, consent decision, automatic erasure proof, dashboard, market result, user cohort or permission to add a third-party SDK.
